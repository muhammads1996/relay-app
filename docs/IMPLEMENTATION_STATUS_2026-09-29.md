# Relay implementation status — 29 September 2026

This records the state of the [UX audit](UX_AUDIT_2026-09-28.md) and [implementation plan](IMPLEMENTATION_PLAN.md). The [production-readiness handoff](PRODUCTION_READINESS_HANDOFF.md) tells the release owner what to provide, decide, run, and verify. This status is not a production-readiness claim.

## Implemented in the current working tree

- Request saves now retain failed/conflicted drafts and prevent a send from silently using older saved data. Responses belong to their originating request tab. The Send control announces saving/sending progress and marks an older response as the previous result while a new request runs. Search, tabs, keyboard navigation, first-run actions, dialogs, compact navigation, accessibility labels, and response tools have been improved.
- Request definitions and environments in schema v2 workspaces are file-backed. UI edits use stable IDs and content hashes; CLI reads the same definitions. SQLite remains the history and index store. There is an explicit path for migration and recoverable file operations.
- Postman, OpenAPI, and curl imports have canonical workspace paths. Bulk imports preview first, require a workspace revision, stage and validate stable-ID files, and recover interrupted commits. The original source and report are retained for successful or non-secret failed bulk commits. Literal credentials in recognized auth fields are rejected before retention.
- Collection runs expose progress, cancellation, elapsed time, and partial results. Cookies, custom CA and client certificates, bounded response previews, streaming downloads in the engine, and a Windows OS-backed Xray credential path have focused coverage.
- Unsaved request recovery copies now survive process restart in bounded local SQLite storage. The editor offers explicit Recover/Discard actions, keeps stale-base conflicts guarded, and clears only a matching copy after a successful save. The [client guide](API_CLIENT_GUIDE.md#unsaved-draft-recovery-and-privacy) explains the plaintext-storage tradeoff.
- Postman query and header rows retain order, duplicates, and disabled state on import. Disabled collection variables are omitted with a warning. A runner-backed fixture covers imported inherited auth and collection/folder/request scripts; unsupported APIs remain reported and retained in the source.
- The workbench shows schema v2 file-scan progress and offers **Refresh files**. Its sidebar renders 300 requests at a time while searching the entire collection. Opening a request reads and hashes only that file, with a stable-ID and safe-path check; its collection and folder IDs come from the same published workspace snapshot.
- A final visual pass tightens type, contrast, spacing, active-state hierarchy, and the connected request/response surface around Relay's indigo identity. Muted text tokens were checked at 6.61:1 and 4.76:1 against white. The latest Send progress and previous-response label were exercised in a local browser fixture. The browser screenshot API returned a zero-width image, so pixel-level and native review are still release gates.

## Verification obtained so far

- The latest `go test -vet=off ./... -count=1` run passed every package except `internal/workspace`: Windows Application Control blocked its generated test executable before execution. Focused external-edit/request-open tests passed before the final symlink guard; after the guard and request-location fix, the UI package passed and the workspace test binary compiled with `go test -c`. CLI and production desktop builds, formatting inspection, inline JavaScript syntax, and whitespace checks passed. Plain `go test ./...` is blocked because this host denies `vet.exe`. Rerun the complete suite and vet on an unrestricted release host.
- A live browser workbench on a disposable schema v2 workspace completed a collection run and cancelled an in-flight fourth request after three passes. The final UI showed **3 finished, 3 passed, 0 failed, 1 cancelled**, with the interrupted request in the detail list and no browser errors. Switching requests during an earlier slow run preserved the editor. A 760×480 browser viewport kept URL and Send reachable and the collection run results scrollable.
- Against the same disposable live server, Postman and OpenAPI preview/commit requests each created a canonical collection. The OpenAPI retained-source endpoint returned the exact uploaded JSON; the Postman commit appeared in the refreshed collection state.
- A live browser recovery check in a disposable v2 workspace showed the explicit recovery prompt, restored a draft as unsaved work, saved it, observed the matching draft row removed, and reopened the request cleanly. A mislabeled cancel action found in that pass was corrected and verified as **Discard draft**.
- A live browser check detected a same-size external file edit with the original timestamp preserved, updated the sidebar and clean open editor, and returned to the original name after a byte-for-byte restore and manual refresh. Focused tests cover scan coalescing, responsive state reads, and stale-save conflicts.
- A reproducible local [performance baseline and optimization check](RELEASE_PERFORMANCE.md) exercised 1,000 and 10,000 request workspaces, a complete streamed 100 MiB download, and 1,000 sequential sends. Batching the request index and parallelizing request-file reads cut the 10,000-request cold `Prepare` from 61.2 to about 5.4 seconds and warm `Prepare` to 3.6–4.4 seconds. A repeated `/api/state` response fell from 8.0 seconds to 72.76 ms. Full file scans still take several seconds, while the browser can search and open request 10,000.
- The native Windows binary can be built, but newly built executables are blocked from launching by this host's Windows Application Control. Browser checks do not substitute for native WebView2 checks.
- The final Send-progress UI edit passed inline JavaScript syntax and CLI embedding/build checks. A local Node-backed browser fixture rendered the latest HTML and verified the disabled **Sending…** control, live status, previous-response label, and completed result; it did not exercise the Go API. The native binary and exact Go-backed browser UI could not start because Application Control blocked both `go run` and the freshly built CLI executable.

## Open release gates

1. Rerun the complete Go suite and `go vet ./...` on a host that permits generated test binaries and `vet.exe`. Run a fresh native Windows application, installer upgrade, file dialog, clipboard, download, scaling, and backup/restore pass on a host that permits the binary.
2. Expand the representative migration corpus. The runner-backed Postman fixture covers common inherited auth, scripts, duplicate fields and disabled rows, but unsupported `pm.*` APIs, OAuth import modes, saved examples and advanced script behavior remain fidelity gaps. OpenAPI YAML and environment migration need explicit acceptance decisions.
3. Wire the existing OAuth and complete-file download capabilities into the editor workflow. Exact history replay needs request and environment snapshots, with a clear retention and secret policy.
4. Complete native workspace opening and recents, and test the entire keyboard-only path. Draft persistence is implemented and browser-smoked, but the pagehide beacon is best-effort. At 760×480 the editor content requires vertical scrolling even though its primary controls are reachable.
5. Measure 10,000-request end-to-end opening, sending, browser interaction, native process memory, startup, idle CPU, and longer repeated-send stability against the [plan's benchmark matrix](IMPLEMENTATION_PLAN.md). State and request-open paths improved, but full file scans still take seconds. No comparative claim against Postman is supported yet.

Do not tag or publish a production release until these gates are verified on the exact release artifact.
