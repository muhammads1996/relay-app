# Relay desktop and application UX audit

Date: 28 September 2026. Source reviewed: `382f4ed`. This is an assessment and implementation backlog; no product code was changed.

**Verdict: Relay has a credible lightweight foundation, but it is not yet a dependable Postman replacement. Its biggest gaps are trust, continuity between workflows, and use of screen space. More features will have limited value until those gaps close.**

The strongest initial market is developers and QA engineers who need local REST workspaces, repeatable tests, and useful CI artifacts without an account. Xray and Playwright export could make Relay particularly useful to QA teams. Trying to replicate every Postman platform feature now would dilute that advantage.

## Evidence and limits

- Inspected the current workbench, desktop entrypoint, HTTP engine, request storage, Postman importer, script runtime, and existing UI audit coverage.
- Interacted with the current `internal/ui/index.html` in Chrome at 1280×820, 1024×760, and 760×480. Used a disposable database and local fixture endpoints only.
- Windows Application Control blocked `go.exe`, so `go test ./...` and a fresh build could not run. Backend experiments used the existing `dist/relay.exe`; matching current source was inspected separately. The binary's embedded UI lacked the current response splitter, so the current HTML was served by an audit-only Node proxy to that backend.
- Executed isolated checks of the actual current JavaScript functions with stubbed network responses to reproduce save failure and late-response behavior. These are focused reproductions, not a complete browser regression suite.
- Native Wails window interaction, installation/upgrade, OS dialogs, clipboard/download behavior inside WebView2, macOS/Linux, live Xray, and desktop memory/startup benchmarks remain unverified. Shared browser UI testing does not certify these desktop behaviors.
- No production workspace, credentials, or external service was used. Screenshots and reproduction scripts are under ignored `test-results/product-audit/`.

Evidence labels below: **Live UI** = current HTML in browser; **Runtime** = existing binary plus matching source; **Harness** = current source function reproduction; **Source** = implementation inspection; **Design** = expert judgment.

## Overall assessment

These are qualitative ratings, not a standardized usability study.

| Area | Assessment | Reason |
|---|---|---|
| Lightweight architecture | Strong foundation | Go, system webview, embedded assets, no frontend framework runtime required |
| Everyday REST workflow | Promising, incomplete | Good editor/response foundations; missing tabs, collection search, cancellation, and cookie sessions |
| Reliability and trust | Release blockers | Save failures, response ownership, misleading settings, migration omissions |
| Visual hierarchy | Needs substantial refinement | Too much persistent chrome and metadata; tiny low-contrast text; cramped primary workspace |
| Test/CI workflow | Differentiated but fragmented | Visual assertions, scripts, exports, Xray; overlapping request/test models and noisy traceability |
| Desktop experience | Thin wrapper today | Shared UI helps maintenance, but workspace/recovery/native affordances need work and native testing |
| Postman migration | High risk | Successful import can silently omit auth and scripts |
| Accessibility | Material gaps | Contrast, interactive tree semantics, modal focus, field labeling |

Keep the shared Go engine, offline operation, readable interchange format, variable provenance, response timing, resizable response pane, visual assertion builder, and useful export formats. These are meaningful foundations.

## Priority 1: fix before positioning Relay as a daily replacement

### F01 — Failed saves do not stop sending or navigation

**Harness + source.** `saveRequest()` catches its exception and resolves normally. Both `send()` and `openRequest()` await it and then continue. A failed PUT was followed by `/api/send` in the reproduction. The user can send the previously stored request while believing the visible edit is being sent, or navigate away after an unsuccessful save.

Evidence: [saveRequest](../internal/ui/index.html), lines 4049–4059; `send`, line 4074; `openRequest`, line 3022. Reproduction: [check-results.json](../test-results/product-audit/check-results.json).

**Change:** propagate save failure; retain the draft; show persistent Saving / Saved / Save failed status and Retry. Capture the request ID and revision before awaiting. Do not clear a newer dirty revision after an older save completes. Rendering a tab must not reset dirty state.

**Acceptance:** simulated offline/422/500 saves cannot produce a send or discard a draft; rapid edits, switching tabs, and closing/reopening recover the latest content.

### F02 — Responses are not owned by the request that initiated them

**Harness + source.** Start A, select B before A completes: `send()` assigns A's response to global `S.last` and loads statistics for the now-current B. The source-function reproduction confirmed this. A live browser attempt did not reproduce the timing window and is not claimed as confirmation.

Evidence: `internal/ui/index.html:4074`.

**Change:** keep execution state and response per request/tab; capture request ID, environment, revision, and an execution token. Render only the result belonging to the active tab. Guard keyboard-triggered sends against duplicate execution. Add Cancel and elapsed time.

**Acceptance:** slow A cannot appear under B; navigating to Settings during a send cannot throw on a missing Send button; repeated Ctrl+Enter cannot accidentally queue duplicate sends.

### F03 — Environment changes render the wrong screen

**Live UI + source.** Open a request, enter Test Management, then select an environment. The regular request editor replaces the test editor, while Suite navigation and test Run controls remain. The handler prioritizes `S.req` over `S.view`.

Evidence: `internal/ui/index.html:2882`; [screenshot](../test-results/product-audit/environment-switch.png).

**Change:** route environment updates through the active view and invalidate only the relevant resolved-variable and execution state.

**Acceptance:** environment changes preserve every view and its current entity, including tests, history, settings, and presets.

### F04 — Settings can contradict the actual network behavior

**Live UI + runtime + source.** Backend settings returned `followRedirects: true`, while the UI checkbox was unchecked. The settings helper passes `checked: ''` for true; the element builder converts it with `!!v`, resulting in false. The same helper renders Skip TLS verification, so an enabled insecure setting would also appear unchecked.

Evidence: `internal/ui/index.html:981` and `4140`; [settings screenshot](../test-results/product-audit/settings.png).

**Change:** pass actual booleans; show an unmistakable workspace indicator when TLS verification is disabled.

**Acceptance:** both true and false values round-trip correctly for every checkbox. TLS state in the editor must agree with the engine.

### F05 — Console logging creates a failed test

**Runtime + source.** A script containing `console.log("debug fixture")` and one passing `pm.test` returned a passing test plus a failed `Script runtime` result. Console output is appended to `RunResult.Errors`, and the UI executor turns each error into a failure.

Evidence: `internal/script/script.go:93`; `internal/ui/ui.go:463`; [backend-results.json](../test-results/product-audit/backend-results.json).

**Change:** separate console messages, runtime exceptions, and assertion outcomes; give scripts a console pane.

**Acceptance:** log/warn output remains inspectable without failing a run; uncaught exceptions and failed assertions still fail correctly across CLI and UI.

### F06 — Move to collection reports success without moving the request

**Runtime + source.** UI sends an updated `collectionId`; `Store.UpdateRequest` updates `folder_id` and request content but omits `collection_id`. A PUT returned 200 while a subsequent GET retained the old collection.

Evidence: `internal/ui/index.html:1296`; `internal/store/store.go:300`; backend reproduction JSON.

**Change:** perform a validated, transactional move; ensure the folder belongs to the destination collection and define the impact on linked tests and inheritance.

**Acceptance:** menu and drag/drop moves survive refresh/restart and use destination headers/variables; invalid cross-collection folder associations are rejected.

### F07 — Postman import silently loses executable behavior

**Runtime + source.** A fixture with collection bearer auth, collection pre-request script, and request test script imported successfully with neither auth nor scripts. The importer structures have no collection/folder auth or event fields and no request event mapping. Request-level common auth is supported; that does not preserve inherited auth.

Evidence: `internal/porter/postman.go:16`; `internal/ui/ui.go:581`.

**Change:** show a migration preview: preserved, converted, unsupported, and skipped. Preserve script scopes and common auth inheritance; surface unsupported `pm.*` APIs before users depend on the collection. Include environment import and OpenAPI YAML in the migration backlog; current UI import accepts JSON.

**Acceptance:** nothing executable is silently dropped. A fixture corpus covers nested folders, auth inheritance, scripts, variables, disabled fields, body formats, and duplicate query parameters. Original imports remain recoverable.

### F08 — UI and CLI have different sources of truth

**Source, documented behavior.** Files seed SQLite initially; UI edits update SQLite; CLI execution reads TOML. The same engine does not make the inputs identical. A user can edit in the desktop, run the original files in CI, and execute stale content. Explicit exports exist, but the interface does not make this boundary prominent.

Evidence: `README.md`, Browser Workbench; `cmd/relay-app/main.go:117`; `internal/store/store.go:300`; `internal/store/seed.go:18`.

**Change:** preferably make request/environment/test definitions file-backed and reserve SQLite for history, indices, and local preferences. If retaining database workspaces, make export/sync state explicit and provide a single reliable Publish to files action with conflict handling.

**Acceptance:** a saved UI edit produces a reviewable file change and identical CLI behavior, or the UI clearly identifies unpublished database changes. External file changes and Git branch switches cannot silently overwrite drafts.

### F09 — The minimum desktop size hides the work area

**Live UI.** At 760×480 in Test Management, navigation occupies 148px, the suite sidebar 280px, and the main area only 28px. Its top bar needs 50px; `#content` has **0px height**. This is the native wrapper's configured minimum size.

At 1024×760 the request workspace is only about 381px wide: method, URL, and Send wrap into separate rows. At 1280×820 the workspace is 566px wide, while navigation/tree/metadata take 663px.

Evidence: `cmd/relay-app/main.go:124`; CSS around `internal/ui/index.html:564`, `866`; [minimum size](../test-results/product-audit/minimum-test-management.png), [1024px](../test-results/product-audit/workbench-1024.png), [1280px](../test-results/product-audit/workbench-1280.png).

**Change:** collapse metadata and navigation before shrinking the editor. Give the main workspace a protected minimum area. Test actual minimum dimensions and high-DPI scaling, not only absence of document overflow.

**Acceptance:** method, URL, Send, active editor, and response remain reachable at every supported size; no zero-height content regions; 125%, 150%, and 200% scaling supported.

## Desktop-specific improvements

The wrapper uses a system webview and directly mounts the same Go handler: a sound way to avoid bundling a second browser engine. The existing desktop executable is **22,854,144 bytes (21.8MiB)** and MSI **7,348,224 bytes (7.0MiB)**. These are existing artifacts, not freshly built measurements, and exclude any separately installed WebView2 runtime.

The wrapper currently takes a workspace via a flag/environment variable/default app-data directory. Add a visible workspace picker, recent workspaces, Open folder, Reveal workspace, and backup/restore. Persist window geometry and editor session. Add native file selection for binary/multipart bodies; typing paths is not an adequate primary desktop flow. Seeded request paths are cleared (`store/seed.go:112`), so the UI's claim that paths are relative to the collection needs explicit root tracking and regression coverage.

Provide a proper About/build version surface, update availability, actionable startup errors, and migration recovery. Startup failures currently go to stderr; that is a poor recovery surface for a Windows GUI build. Treat window close as a draft-flush/recovery boundary.

Validate native copy/paste, Save As/downloads, import dialogs, keyboard conventions, zoom/DPI, resize, multiple app instances, sleep/resume, upgrade and database backup/restore on Windows. Then repeat the supported subset on macOS/Linux. Do not assume success in Chrome certifies WebView2 or WKWebView.

## Proposed interaction and visual direction

**Make Relay feel like a focused developer instrument.** Keep the restrained indigo identity, but make the request and response dominate. The current many-card presentation creates unnecessary borders, padding, and separate scroll regions.

```text
 Workspace / project                  Search commands       Environment
 ┌────┬──────────────────────┬────────────────────────────────────────┐
 │API │ Search requests      │ Health ×  Create user ×  +             │
 │Test│ Collection tree      ├────────────────────────────────────────┤
 │Hist│                      │ GET  https://...             Send ▾    │
 │    │                      │ Params  Auth  Headers  Body  Tests     │
 │    │                      │ Editor                                 │
 │    │                      ├──────────── resizable ────────────────┤
 │    │                      │ 200 OK · 24ms · 1.2KB   Body Headers… │
 │    │                      │ Response                               │
 └────┴──────────────────────┴────────────────────────────────────────┘
 Saved locally                           Optional console / details drawer
```

- Use an approximately 48px navigation rail and resizable 220–280px collection tree. Keep metadata in a drawer. At 1280px, target roughly 900px for the work surface.
- Keep method, URL, and Send together at laptop widths. Overflow secondary actions before wrapping the primary flow.
- Simplify response actions: Pretty/Raw, Wrap, Search, Copy, and an overflow menu. Move format conversion out of the primary row. Add JSON collapse, JSONPath navigation, and response diff before more cosmetic formats.
- Use consistent vector icons; replace platform-dependent emoji and ambiguous symbol-only controls. Use one spacing scale and fewer enclosing cards.
- Make “API client” and “Tests” clear modes. Test configuration should reuse the request editor components and show explicit inherited/overridden values.
- Add light/dark/system themes only after semantic color tokens and contrast are corrected. Preserve saved density, pane proportions, tabs, and selection.

## Competitive position

“No account” alone is insufficient positioning: Postman offers an unsigned-in lightweight client for HTTP, WebSocket, gRPC, and GraphQL. Its local-use documentation also describes Native Git, requiring sign-in, and limitations on the lightweight client's collections/environments. [Postman lightweight client](https://learning.postman.com/latest-v-12/docs/getting-started/basics/using-api-client), [local-use documentation](https://support.postman.com/hc/en-us/articles/115003356485-Can-I-use-Postman-locally).

Bruno is an especially relevant competitor because filesystem collections and Git workflows are central to its product. Relay's database/file divide weakens that comparison today. [Bruno](https://www.usebruno.com/).

| Buyer need | Relay today | What would make Relay compelling |
|---|---|---|
| Quick REST request, no account | Good foundation | Faster first send, reliable drafts, strong response inspection |
| Switch from an existing Postman workspace | High migration risk | Compatibility report and tested preservation of common behavior |
| Git review and CI reproducibility | CLI files good; UI diverges | Shared canonical definitions and deterministic runs |
| Enterprise authentication | Bearer/basic/API key | OAuth2, cookies, certificates, secret-store UX |
| QA workflow | Rich starting feature set | Clear request/test inheritance, reliable console/assertions, excellent run results and exports |
| Minimal resource use | Small distribution and good architecture | Published, reproducible startup/RAM/CPU and large-workspace benchmarks |
| Multiple protocols | HTTP engine; raw GraphQL-over-HTTP possible | Add dedicated protocol UX only for validated customer demand |

Postman already documents mature [OAuth2 flows](https://learning.postman.com/docs/use/send-requests/authorization/oauth-20), [client certificates](https://learning.postman.com/docs/getting-started/installation/settings/certificates), and [cookie management](https://learning.postman.com/latest-v-12/docs/use/send-requests/response-data/cookies). These are practical switching requirements for many teams.

Recommended promise: **“A fast local API workbench that turns requests into reliable, versioned tests and CI artifacts.”** Earn this through file continuity, migration fidelity, and trustworthy execution. Delay cloud collaboration, monitors, mock infrastructure, and broad protocol expansion until the REST/QA workflow is excellent.

## Lightweight engineering and measurable targets

Small install size is only one dimension. Runtime memory, idle CPU, large collections, large responses, and interaction latency need measurement. No comparative Postman or native Relay RAM/startup result was obtained in this audit.

Source-level concerns: a new transport/client per send forfeits connection reuse across sends; no explicit idle-transport cleanup is present. Full sidebar rebuilding and loading all collection metadata will become expensive with large workspaces. Synchronous syntax highlighting/formatting can block interaction. Bodies are buffered, with different engine/UI/history limits. History retention is already bounded at 500, which is a useful starting point.

Reuse appropriately scoped transports, bound caches, virtualize long trees/results, and use incremental rendering. Introduce workers or lazy loading only where measured. Splitting the roughly 270KB single HTML source into maintainable modules does not require adopting a heavy framework; assets can still be embedded in the binary.

Proposed release targets, to calibrate against reference hardware:

| Scenario | Initial target |
|---|---|
| Warm launch to usable editor | under 1 second |
| Cold launch to usable editor | under 2 seconds |
| Idle CPU after settling | under 1% |
| Idle desktop private working set, including attributable webview processes | aim below 150MiB; measure and publish |
| Switch request with 1,000 saved requests | p95 under 100ms |
| Search 10,000 request metadata records | p95 under 100ms after indexing |
| 1MiB JSON response | no sustained typing/navigation stall; cancellable formatting |
| 100MiB download | bounded memory; explicit preview truncation; complete streamed file |
| Repeated sends/runs over 30 minutes | memory reaches a plateau; no accumulating idle sockets/goroutines |

Measure identical datasets and hardware for Relay/Postman/Bruno; include all child processes and separate cold/warm results. Treat these numbers as engineering targets, not marketing claims.

## Implementation order and release gates

1. **Trust and correctness:** F01–F07, F10, settings truth, view-aware shortcuts, recoverable drafts. Add failure-injection, delayed-response, navigation, migration, and checkbox regressions.
2. **One coherent daily workspace:** resolve F08; tabs, search, cancellation, layout collapse, accessible controls, readable contrast, clear error/empty states. Test 760×480 through wide desktop and OS scaling.
3. **Practical switching parity:** OAuth2, cookies, certificates, duplicate query/header handling, script console, import compatibility report, environment migration, exact history snapshots.
4. **QA advantage and desktop polish:** simpler test authoring, explicit overrides, progress/partial results, export fidelity, workspace chooser, secret store, recovery/update UX, native cross-platform verification.
5. **Prove lightweight behavior:** automate the benchmark matrix, set budgets, and publish measurements before expanding the product surface.

Existing UI tests check overflow and a request/response flow, but omit the 760×480 native minimum, save failures, delayed responses, many navigation transitions, keyboard-only completion, migration fidelity, and actual native dialogs. Some tests assert source strings; those cannot establish user-visible correctness.

Release gate: five representative users can import or create a collection, configure an environment/auth, send requests, diagnose a failure, add tests, run the suite, and reproduce it in CI without assistance or unexplained behavior. Observe task completion, time, errors, and recovery—not whether users merely like the appearance.

**Recommendation:** pause feature expansion for a reliability and workflow release. Fix the confirmed defects, reclaim the main workspace, and make UI-to-CLI continuity explicit. That will do more for a credible Postman alternative than adding another navigation item.
